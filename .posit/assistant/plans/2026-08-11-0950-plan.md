# Plan: Drive cache refresh timing for DreamLeague Shiny app

## Goal
Improve the Shiny app cache so it persists the last Google Drive check time, avoids repeated remote listings within an hour, and adds a manual refresh control in the Diagnostics sidebar.

## Current state
- The app entry point is `dreamleague/app.R`.
- Cache files are stored under `cache/` and currently loaded at startup.
- `ensure_drive_cache()` already checks local file age against a one-hour staleness window and downloads from Google Drive if the local copy is stale and the remote file is newer.
- The Diagnostics tab currently shows cache status but has no refresh button.

## Proposed implementation
1. **Add persistent cache metadata**
   - Store a small metadata file alongside the cache, likely in `cache/`.
   - Persist at least:
     - last remote check time
     - last remote check result (`success` / `failure`)
     - last successful remote pull time
     - last known cache refresh time
     - whether the last refresh was forced
     - the last remote error message when a check fails
   - Load this metadata at app startup if it exists; initialize it safely if it does not.

2. **Refactor cache bootstrap into an explicit refresh helper**
   - Create a helper that:
     - checks the persisted last remote check time
     - if the last remote check was within the previous hour, uses the local cache without listing Drive
     - if more than an hour has elapsed, performs a remote Drive listing
     - compares remote file modified times with local cache times
     - downloads only when remote files are newer
     - updates the persisted metadata after each check attempt, successful or not
   - Keep the existing one-hour policy, but move the decision from local file age to the persisted remote-check timestamp.

3. **Add a forced refresh path**
   - Add a helper path that bypasses the hourly check and always queries Drive.
   - If the remote files are newer, download them and refresh the cache metadata.
   - Update the check timestamp even when the remote files are unchanged, because the remote was explicitly checked.

4. **Expose a Diagnostics sidebar button**
   - Add a button to the Diagnostics tab sidebar, for example `Force refresh from Google Drive`.
   - Wire the button to the forced refresh helper.
   - After refresh, update the cache status display so the user can see the new check time and source.

5. **Refresh app state after cache changes**
   - Ensure any objects loaded from the cache are reloaded after a successful forced pull.
   - Verify that the app uses the updated in-memory data without requiring a full app restart.

6. **Update diagnostics text**
   - Show at least:
     - last remote check time
     - last refresh time
     - whether the current data came from local cache or Google Drive
   - If the last remote check failed within the previous 24 hours, display a warning message in the Diagnostics tab.
   - If helpful, distinguish between “remote checked, no newer files found” and “pulled from Google Drive”.

7. **Validate behavior**
   - Test these cases:
     - first app start with no metadata file
     - app start within an hour of the previous remote check
     - app start after more than an hour
     - force refresh from the Diagnostics sidebar
     - remote files unchanged vs newer than cache
     - failed remote check followed by a restart within 24 hours

## Notes / assumptions
- The metadata file can be created inside `cache/` without affecting existing data files.
- The bundled-cache fallback behavior should remain when Drive is unavailable.
- The plan now assumes the persisted timestamp represents the **last remote check attempt**, successful or not.
- The diagnostics warning should be based on that same check timestamp plus the last check result.
